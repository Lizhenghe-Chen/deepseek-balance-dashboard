# 测量精度与消费口径

> 返回 [README](../README.md) · 相关：[数据模型](./data-model.md) · [FAQ](./faq.md)

## 📏 测量精度

余额接口只返回 **2 位小数的字符串**，这是所有消费数字的物理下限：

| 量 | 精度 |
|---|---|
| 最小刻度 | ¥0.01；单次读数误差 ±¥0.005 |
| 本月合计（链式求差） | 误差 **≤ ¥0.01**（中间误差精确抵消，与天数无关） |
| 单个「日」 | 每天重新起链 → 各自 ±¥0.01，**还会叠加**「页面未打开期间的整段消费记到重开那一刻」的缺口 |
| 日消费 ¥0.29 | 一个台阶要等约 49.7 分钟，分钟轴上会是一段直线；这个量级适合看日 / 月，不适合看分钟 |
| 日消费 ¥7 | 一个台阶约 2 分钟，分钟轴上勉强能看出阶梯 |
| 台阶落点 | 前台每分钟采样 → 每笔的位置误差约 ±1 分钟；后台 5 分钟采样 → ±5 分钟 |
| 日消费 < ¥0.005 | 可能整天显示 ¥0.00，图表 tooltip 会说明「低于可测精度」 |

因此「预计可用 N 天」以**区间**呈现（例如 `85–87 天`）：只要日均偏一个刻度，天数就会大幅跳动。样本不足 3 天时页面不给预测，只写「样本不足」，避免用一天的消费外推出「还能用两百多天」这种伪精度。

需要精确到分时，导入控制台「用量信息」导出的 CSV 即可——已过去的整天会改用官方日成本，主卡与各项统计都会跟着变（趋势图仍按采样落点画，保证台阶细节）。

## 📐 消费是怎么算出来的

官方文档明确：`total_balance = granted_balance + topped_up_balance`，且扣费时**优先扣赠送额度**。因此：

- ✅ 用 `total_balance` 跟踪余额。若只看 `topped_up_balance`，赠送额度没花完时消费会一直显示 **0**。
- ✅ 消费 = **相邻两次采样余额差值的累加**，而不是「当天首尾差」。后者一旦中途充值，当天消费会被抹成 0。
- ✅ 充值（余额上升）单独统计为「期间充值」，绝不冲抵消费。
- ✅ **导入官方 CSV 后按天覆盖**：已过去的整天改用官方日成本（`cost-*.csv` 的金额，或 `amount-*.csv` 的 `price × amount`），没有官方数据的天仍用观测值。**今天取官方与观测的较大值**——官方文件只到导出那一刻、观测只覆盖页面打开之后，取较大值才不会让当天数字变小；另一路数字降级为「本日消费」下方的一行备注。
- ⚠️ 官方数据是**导出时刻的快照**，不会自动更新；看到新的消费要重新导出并导入。同一账户重复导入同名文件会更新那一条批次，不会翻倍。
- ⚠️ 导入可能来自不同账户：每个批次都显示 `user_id`，多个账户混在一起时会给出提示，删掉不属于当前账号的那条，主数据里对应日期会立刻退回观测值（或被更早的批次接管）。
- ⚠️ 官方日按**本地日期**归属（`start_time_iso` 带时区偏移，换算到浏览器本地时区）；币种与当前账号不一致时不会合并。
- ⚠️ **隔夜变动会整体记入「重新打开页面」的那一天**：那一笔会画在当天的第一个点上，并在副标题标注「含隔夜缺口」，无法真的拆分到前一晚。
- ⚠️ 日均的分母是「从第一个有数据的那天算到今天」的**日历天数**，中间没打开页面的日子也计入。
- ⚠️ 官方自 2026-08 起实行**峰谷价**（空闲价 = 高峰价的一半，高峰为北京时间周一至周五 09–12、14–18），所以同样多的 token 在不同时段花费不同，日消费忽高忽低属于正常。

## 🧭 已知失真

- 赠送额度过期也会让 `total_balance` 下降，会被记为当天消费。
- 页面未打开期间无法采样：总量仍会体现在下一次采样里，但无法得知具体发生在哪一刻（在曲线里表现为第一个点跳得特别高，并标注「含隔夜缺口」）。
- 余额精度为 2 位小数，因此小于 `¥0.01` 的消费不可见；详见上面的「测量精度」。
- `localStorage` 写满时会先丢最老账户的一半采样，再不行丢掉整份最老账户，链式差值因此出现硬缺口（极少数情况）。
- 多账户档案之间**没有关联**：同一账户的多个 Key 各记一份，消费不可相加；不同账户之间也不做任何合并。
