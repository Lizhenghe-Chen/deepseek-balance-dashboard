## 🔁 多账户 / 切换 / 后台采样

每个 Key（配合币种）一份独立档案，**互不做差、互不覆盖**。最多 5 个账户，每份保留 60 天。

### 添加账户

点顶栏 `⚙️`，在输入框粘贴 Key 后保存：

- 粘贴**已存在**的 Key → 直接切回它那份历史；
- 粘贴**新** Key → 新建一份档案，从这一刻开始记录，其它账户原样保留。

### 直接切换，不用重输 Key

页面维护一张**本标签页的 Key 环**（`sessionStorage` 的 `ds_keys`）：凡是这个标签页里粘贴过的 Key 都会留在环里，所以

- 主卡上的下拉（账户多于 1 个时出现）可以直接换账户；
- `⚙️` 面板每一行也有「切换」按钮。

切换会立刻用该账户的 Key 刷新一次，曲线、卡片、日均都跟着换。关掉标签页，环里未"记住"的 Key 就消失（历史仍在，重输一次 Key 即可）。

如果某个账户的 Key 已被撤销 / 过期（接口返回 401，通常是已撤销、过期，或粘贴时截断了），切换时**不会弹设置面板打断**：状态栏会说明原因，下拉与列表里该账户标「Key 失效」，页面照常显示它的历史但不再自动刷新。重新粘贴有效 Key 或点顶栏 `↻` 手动重试即可恢复（成功后自动清掉标记）。**只有一种情况会主动弹面板**：整个浏览器里一个 Key 都没有（第一次使用）。

### 让某些账户继续在后台记录

默认只有**当前显示的账户**在采样，其它账户的历史是冻结的。想让某个账户也一直记录，就得**显式打开**——因为页面里只有 Key 的指纹、没有 Key，不打开就发不了请求。在 `⚙️` 面板给它点「后台」（或勾上输入框下方的「记住这个账户的 Key，并在后台继续采样」）：

- **后台采样**：即使不显示它，也会继续写采样。频率比当前账户低（可见 5 分钟 / 隐藏 15 分钟）——它们的曲线是拿来看趋势的，没必要为 ±1 分钟落点付 N 倍请求；
- **记住 Key**：该账户的明文写进本机 `localStorage`（`ds_keys_saved`），重开页面、换标签页都能直接刷新和切换；
- 每个 Key 独立做 429 退避，一个被限流不会拖慢其它账户；
- 关掉「后台」会立刻把那份明文从 `localStorage` 删掉，本标签页内仍可切换。

> ⚠️ **同一账户的多个 Key 共享同一个余额池**。它们各自独立记一份观测序列没问题（不会互相做差产生假消费），但**不要把它们的消费相加**。要"一个账户一个总额"，就只留一个 Key 的记录。

> 币种不同会按 `指纹|币种` 各存一份，CNY 与 USD 的历史不会混算。同一账户的 Key 在环里以指纹为键，切币种不需要额外输入。

### 重命名与删除

账户名默认取指纹前 6 位，在 `⚙️` 列表里**点名字**即可改成你能认出来的（导入过官方 CSV 的话会自动用里面的 `user_id`）。删除是两段式确认（点一次变「确认删除」，4 秒内再点才生效）——历史删掉就只能靠导出的 JSON 找回。

## 🔎 趋势图：缩放 / 定位到某个时刻 / 拖动

图上默认画"到此刻为止"的一段。想回看之前的精确区间，有三种方式：

- `−` / `＋`：放宽 / 收窄跨度，最细 30 分钟，右端始终是**当前时刻**；
- `⏱`：弹出一个「截止到」时间框，选好时刻后，图就显示**那个时刻之前的 N 分钟/小时/天**，再用 `−` / `＋` 调 N。旁边还有「最近一次消费」「最近一次变动」两个快捷跳转，以及「回到现在」；
- 直接在图上**左右拖动**：平移时间窗口（拖动方向就是时间推移的反方向），本质是改上面那个截止时刻。

定位之后，跨度按钮旁的胶囊会变成截止时刻（如 `11/4 16:17`），点击即可修改或回到现在；标题下方同时写明「查看 11/4 14:17 → 16:17」。日均消耗也跟着这个区间算，副标题标注「11/4 16:17 为止」。

> 「本月消费」「本日消费」仍按**日历**统计今天/本月，不随定位变化——它们回答的是"今天花了多少"，不是"这段区间花了多少"。
> 跨度停在被关闭的那段时间里时，图会是空白并提示「这段时间还没有采样」，不会凭空连线。

## 🧾 官方用量 CSV

1. 打开 <https://platform.deepseek.com/usage> →「用量信息」→ 选时间范围 → **导出**；
2. 解压得到 `amount-*.csv` 与 `cost-*.csv`；
3. 在页面「官方用量」面板点「导入 CSV」，可多选两个文件，也可以直接把文件拖进面板。

导入后：

- 已过去的整天改用官方日成本（`本月消费`、日均、预测都会跟上），副标题标注「官方 N/M 天」，避免整月被误读为精确值；
- 面板给出官方本月 / 今日成本、缓存命中率、请求数、分模型成本，以及「官方 vs 观测」的对账差；
- 今天仍用实时观测，若与官方快照不同会同时列出两个数字；
- 每次导入单独成一条（文件名 / `user_id` / Key 名称 / 覆盖的日期范围 / 天数与行数 / 金额 / 导入时间），可删除，删除后 8 秒内可撤销（「全部删除」同样可撤销）；
- 没导入时这块只占标题一行，不会占掉首屏；全部删完后主数据回到纯观测口径。

只导 `amount-*.csv` 也能算成本（用文件里的 `price × amount`），但该文件不带币种列，此时按当前账号的币种理解；导 `cost-*.csv` 则使用官方金额与币种（同一天可能分 Paid / Granted 两行，会求和）。

几个容易踩的点：

- 导错了账户（`user_id` 不同）能一眼看出来——面板会提示「检测到 N 个不同账户的用量文件」，点那条后面的「删除」即可，主数据里对应的日期会**立刻回退**成观测值（若还有更早的导入覆盖同一天，会退回到那份的值）；
- 同一账户重复导入同名文件 = 更新那一条，不会并列、也不会翻倍；
- 币种与当前账号不一致的文件会标「未合并」，只列出、不影响主数据；
- 文件里的 `api_key` 列**不会被读取**，也不会落盘。

## 🔔 低余额提醒

在 `⚙️` 面板里填阈值并点「开启 / 更新」，浏览器会请求通知权限；余额跌破阈值时发一次桌面通知，回升后再跌破会重新提醒。

限制（页面会如实标注）：只在页面打开时生效；后台标签页可能延迟到约 1 分钟；手机锁屏 / 关闭浏览器不会触发；iOS Safari 需要把页面「添加到主屏幕」且走 Service Worker，本页用的是普通 `Notification`。想要「关掉浏览器也能提醒」，只能用服务端方案（例如 GitHub Actions 定时轮询）。

## 💾 历史备份与迁移

- 顶栏「导出历史数据」把**全部账户**与官方用量写成一份 JSON；「导入历史数据」按档案合并（同一天以时间戳并集为准），旧版单档案 JSON 同样可导入。
- 数据按**来源（origin）**隔离：在线版与本地版（`file://`）互不相通，`https://bunnychen.top/…` 与 `https://<用户名>.github.io/…` 也各自独立。跨设备 / 跨浏览器请走导出 / 导入。
- 想从零开始：在 `⚙️` 里删掉对应账户，或清掉浏览器的 `ds_history_v3`。

## 📏 测量精度与消费口径

余额接口只返回 **2 位小数的字符串**，这是所有消费数字的物理下限：

| 量 | 精度 |
|---|---|
| 最小刻度 | ¥0.01；单次读数误差 ±¥0.005 |
| 本月合计（链式求差） | 误差 **≤ ¥0.01**（中间误差精确抵消，与天数无关） |
| 单个「日」 | 每天重新起链 → 各自 ±¥0.01，**还会叠加**「页面未打开期间的整段消费记到重开那一刻」的缺口 |
| 日消费 ¥0.29 | 一个台阶要等约 49.7 分钟，分钟轴上会是一段直线；这个量级适合看日 / 月，不适合看分钟 |
| 日消费 ¥7 | 一个台阶约 2 分钟，分钟轴上勉强能看出阶梯 |
| 台阶落点 | 前台每分钟采样 → 每笔的位置误差约 ±1 分钟；后台 5 分钟采样 → ±5 分钟 |
| 日消费 < ¥0.005 | 可能整天显示 ¥0.00，图表 tooltip 会说明「低于可测精度」 |

因此「预计可用 N 天」以**区间**呈现（例如 `85–87 天`）：只要日均偏一个刻度，天数就会大幅跳动。

### 日均怎么算

日均**跟着趋势图当前的跨度走**：图上是近 2 小时就按 2 小时的趋势估，近 6 小时就按 6 小时估，点 `−` / `＋` 缩放趋势图即可切换；用 `⏱` 把图定位到过去的某个时刻时，日均只统计**那个区间**（副标题会写「M/D HH:MM 为止」）。分母是这段跨度里「首采样 → 末采样」的实际时间，不是日历天数：

- 只观测了 1.3 小时却除以 5 个日历日，日均会被稀释成 1/90，「预计可用」跟着膨胀成几百天——所以页面宁可按 1.3 小时折算；
- 页面关闭期间的消费会在重开时以一次差值出现，而「跨度」本来就覆盖那段时间，所以这个口径既不会漏掉缺口，也不会把没花钱的时间重复计入；
- 跨度不足 6 小时时预测只标「仅供参考」，不足 15 分钟干脆不给数字（两个点除出来全是噪音）；
- 趋势图窗口的两端会被夹到「有采样的范围」里，所以数据早就停了（比如停在 4 天前）时，缩到「近 24 小时」会如实说「没有足够采样」，而不是拿空白时段当分母。

需要精确到分时，导入控制台「用量信息」导出的 CSV 即可——已过去的整天会改用官方日成本，主卡与各项统计都会跟着变（趋势图仍按采样落点画，保证台阶细节）。

### 消费是怎么算出来的

官方文档明确：`total_balance = granted_balance + topped_up_balance`，且扣费时**优先扣赠送额度**。因此：

- ✅ 用 `total_balance` 跟踪余额。若只看 `topped_up_balance`，赠送额度没花完时消费会一直显示 **0**。
- ✅ 消费 = **相邻两次采样余额差值的累加**，而不是「当天首尾差」。后者一旦中途充值，当天消费会被抹成 0。
- ✅ 充值（余额上升）单独统计为「期间充值」，绝不冲抵消费。
- ✅ **导入官方 CSV 后按天覆盖**：已过去的整天改用官方日成本（`cost-*.csv` 的金额，或 `amount-*.csv` 的 `price × amount`），没有官方数据的天仍用观测值。**今天取官方与观测的较大值**——官方文件只到导出那一刻、观测只覆盖页面打开之后，取较大值才不会让当天数字变小；另一路数字降级为「本日消费」下方的一行备注。
- ⚠️ 官方数据是**导出时刻的快照**，不会自动更新；看到新的消费要重新导出并导入。同一账户重复导入同名文件会更新那一条批次，不会翻倍。
- ⚠️ 导入可能来自不同账户：每个批次都显示 `user_id`，多个账户混在一起时会给出提示，删掉不属于当前账号的那条，主数据里对应日期会立刻退回观测值（或被更早的批次接管）。
- ⚠️ 官方日按**本地日期**归属（`start_time_iso` 带时区偏移，换算到浏览器本地时区）；币种与当前账号不一致时不会合并。
- ⚠️ **隔夜变动会整体记入「重新打开页面」的那一天**：那一笔会画在当天的第一个点上，并在副标题标注「含隔夜缺口」，无法真的拆分到前一晚。
- ⚠️ 日均用的是**观测跨度**（见上文「日均怎么算」），所以它描述的是「这段时间里平均每天花多少」，不是「这个自然月平均每天花多少」。
- ⚠️ 官方自 2026-08 起实行**峰谷价**（空闲价 = 高峰价的一半，高峰为北京时间周一至周五 09–12、14–18），所以同样多的 token 在不同时段花费不同，日消费忽高忽低属于正常。

### 已知失真

- 赠送额度过期也会让 `total_balance` 下降，会被记为当天消费。
- 页面未打开期间无法采样：总量仍会体现在下一次采样里，但无法得知具体发生在哪一刻（消费曲线里表现为第一个点跳得特别高，并标注「含隔夜缺口」）。余额曲线则从缺口之后的第一次采样开始画，缺口那段留白，不把旧余额平铺过去。
- 余额精度为 2 位小数，因此小于 `¥0.01` 的消费不可见；详见上面的精度表。
- `localStorage` 写满时会先丢最老账户的一半采样，再不行丢掉整份最老账户，链式差值因此出现硬缺口（极少数情况）。
- 多账户档案之间**没有关联**：同一账户的多个 Key 各记一份，消费不可相加；不同账户之间也不做任何合并。

## ❓ 常见问题

<details>
<summary><b>为什么一开始图表是空的，或者消费显示 0？</b></summary>

消费由两次采样的差值推导，至少需要两次「余额发生变化」的采样。刚设置好 Key 时只有一个点，稍等一轮刷新即可。
</details>

<details>
<summary><b>关掉浏览器还会继续记录吗？</b></summary>

不会。这是纯前端方案，没有后台进程；这是它保持「零部署」的代价。
</details>

<details>
<summary><b>明明有账户记录，为什么还让我填 Key？</b></summary>

记录的是**历史档案**（余额快照 + Key 指纹，不含 Key），Key 默认只活在当前标签页。换标签页 / 重开浏览器 / 换浏览器时历史还在、Key 没了，所以会提示。此时页面会照常用历史渲染、不会弹窗催你；勾选「记住 Key」即可让下一个标签页直接刷新。
</details>

<details>
<summary><b>刷新会丢数据吗？</b></summary>

不会。刷新保留 Key（`sessionStorage`）与历史（`localStorage`），并立即重新拉取一次余额。
</details>

<details>
<summary><b>换了 API Key，历史会怎样？</b></summary>

什么都不丢。每个 Key 对应一份独立档案：粘贴**已有的** Key → 直接切回那份历史；粘贴**新的** Key → 新建一份，从此刻开始记录，旧的原样保留。

要注意两点：① 账户名默认取指纹前 6 位，建议在 `⚙️` 里改成你能认出来的名字（导入过官方 CSV 的话会自动用里面的 `user_id`）；② 同一账户的多个 Key 共享余额池，两份档案的消费**不能相加**。
</details>

<details>
<summary><b>我的账号同时有 CNY 和 USD，显示哪一个？</b></summary>

页面**只跟踪一种币种，绝不求和**。规则是：优先沿用已记录的币种（避免接口数组顺序变化导致抖动），否则取有充值余额的那个，再否则取有余额的那个。另一种币种会以「另有 USD $x」的形式显示在主卡副标题里。若接口只返回另一种货币，会切到 `指纹|USD` 那份档案（没有就新建），CNY 的历史原样保留，并在状态栏提示。
</details>

<details>
<summary><b>图表的跨度是怎么定的？</b></summary>

默认就是**你实际记录到的范围**：只有 2 小时数据就画 2 小时，有 6 天就画 6 天，不会强制一周。

- 想看得更细：点 `＋` 收窄跨度（最小 30 分钟），`−` 放宽，点中间的文字（如「全部 6 天」）回到全程；
- 跨度变大时**不会突然变成每天一个点**：先按采样画（台阶落点精确到分钟），只有当窗口里的台阶多到一屏看不清（> 600 级）才按 5/15/30 分钟、整点、整天逐级聚合，并在标题下方注明「按 N 小时聚合」；
- 采样很稀的时候（比如页面只开过几分钟），台阶会很大——这不是 bug，是余额只有两位小数的必然结果；
- 窗口起点前如果没有采样（页面当时没开着），曲线**从缺口之后的第一次采样开始画**，不会把更早的旧余额平铺过来：否则那个旧高点会把整根纵轴撑大，把后面的细节压成一条线。标题下会注明「起点前有缺口，数据从 X 起」；
- 想看**之前某个时刻**的近 N：点 `⏱` 选截止时刻，或者直接在图上左右拖动，见上文[趋势图](#-趋势图缩放--定位到某个时刻--拖动)。
</details>

<details>
<summary><b>为什么悬停有时报的是指针这一刻，有时报的是某个时间点？</b></summary>

曲线是台阶：竖直段表示余额在这一刻变了，水平段表示余额没变。

- 指针落在**竖直段**上（陡降 / 陡升，屏幕上常常只有一两像素宽）时，按指针高度分上下半：指在下半段选下面的端点，指在上半段选上面的端点。所以一笔瞬时大额消耗跌到的最低点、以及随后的充值顶点，都能各自选出来；
- 指针落在**水平段**上时，tooltip 跟着指针走，时间取指针所在的时刻，并额外说明「自 MM/DD HH:MM 起未变动」——那一段的余额是沿用台阶起点的，不是这一刻又变动了一次。

聚合到按小时 / 按天时，每个桶都是一个点，判定规则相同：桶内没有变动就显示「这一档没有记录到消费」或「这一档余额没有变动」。
</details>

<details>
<summary><b>余额趋势里的台阶怎么来的？</b></summary>

余额是逐级下跌的阶梯：每笔消费扣掉 ¥0.01 的整数倍。向上的台阶是**充值或赠送到账**，不是收入统计；关掉页面期间的花费会整体记到重新打开的那一刻。
</details>

<details>
<summary><b>提示「图表库未加载」？</b></summary>

说明 Chart.js 没能从 CDN 取到（离线或被网络策略拦截）。此时数据刷新、导出、用量导入仍然可用。若要改成完全离线：把 `chart.umd.js` 下载到同目录，改掉 `<script src>`，并且**把 CSP 的 `script-src` 加上 `'self'`**（当前只允许内联脚本与 jsDelivr，直接换成本地文件会被 CSP 拦下）。
</details>

<details>
<summary><b>为什么前台 1 分钟、后台 5 分钟？</b></summary>

前台 1 分钟是为了让「今日消费曲线」的台阶落点准到 ±1 分钟；切到后台后浏览器本来就会节流定时器，继续 1 分钟只是空转，所以降到 5 分钟（同时把请求量从约 1440 次/天降到 288 次/天）。

余额只有 2 位小数，所以曲线永远是台阶：**每 ¥0.01 一跳**。日消费 ¥7 左右时大约 2 分钟一级，分钟轴有意义；日消费不到 ¥1 时，一小时才一两级，这时看日 / 月更合适——这不是隐藏，页面会如实显示台阶。
</details>

<details>
<summary><b>1 分钟一次会不会把 API 调爆？</b></summary>

整天开着标签页约 1440 次/天。项目里对 429 做了退避：触发限流后先退到 5 分钟，连续触发最长退到 15 分钟，不会死循环重试。如果你更在意请求量，把 `POLL_VISIBLE` 改回 `5 * 60 * 1000` 即可，曲线仍然可用，只是台阶落点变粗。
</details>
